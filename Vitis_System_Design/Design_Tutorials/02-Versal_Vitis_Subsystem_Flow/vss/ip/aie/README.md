# AI Engine graphs and kernels

To demonstrate how AI Engine kernels behave when interacting with programmable logic, processor subsystem and DDR memory controllers the tutorial use a small subsystem showing some variants of data flow signal processing.
The AI Engine design is represented by a top graph, which consists of a datamover subgraph (using 2 channels) and a FIR filter subgraph with two instances of a 16 tap FIR filter.
These examples are easy to explore, yet demonstrate key aspects a system designer should pay attention to.

### Principle of operation for the data mover channels
The datamover subgraph takes inputs generated by a freerunning counter that runs regardless of back pressure stall signalling.
The purpose for this is to:
  - Visualize how data propagates through the AIE design and measure latency caused by execution.
    - Verify data correctness.
    - Compare different access mechanism like buffer API and stream API.
    - Compare latency differences caused by mapping placement and how to mitigate with constraining the placement.
  - Examine effects of AXI Stream protocols and AIE kernel call invocations.
    - Finding and analyzing stalls and backpressure.
    - Startup behavior and steady state of continuous processing.
    - Backpressure and data starvation propagating from AIE to PL.

### Compile and build AIE design
For the global project settings and paths to work, always build the AIE ip from the design root directory.
The AIE is compiled as part of the vss rule from top [Makefile](../../../Makefile)
```
make vss
```

To compile AIE separately, use the following command and replace overriding parameters (PART & FREQHZ) with suitable values.
```
make all -C vss/ip/aie PART=${PART} FREQHZ=${FREQHZ}
```

## Detailed example description


### AI Engine datamover examples
**Note** These examples originate from thin custom platform tutorial and this lab use two of the mentioned data mover kernels for demo purpose.

These AI Engine kernel examples demonstrate a few different coding techniques using datamovers as case study.
They also show how to optimize the kernel processing to allow for efficient processing of data with the inner loops.
By modifying the graph and constraints file, the kernel examples can be put in different comparison contexts for learning purpose.

Note that the graph have been converted to use C++ class style kernels.

### Object oriented C++ template class kernels with AI Engine API style
The current graph create 4 individual data paths each moving data from PL through an instance of a datamover kernel back to PL.
By using template C++ class kernels, the data type can be changed when instantiating the kernel in the graph.
The AI Engine API enables portable code across AI Engine device families (AIE and AIE-ML) and is easier to use than intrinsics API.

Note that these examples are basic with focus on readable and compact code using helper functions like vector iterators.
For optimization, techniques used in the old function style kernels can still be applied, but may require mixing AIE API with intrinsics.
```
  0. my_scalar_dm.cpp       : Uses AIE scalar processing to move 32-bit data (cint16) each clock cycle. The data is moved
                              from input to output using scalar iterators.
  1. my_vector_dm.cpp       : Uses AIE vector processing to move 256-bit data (8 lanes of cint16) each clock cycle.
                              The vector registers is used for temporary storage declared as a vector iterator.
  2. my_mul_dm.cpp          : Similar as vector data mover, except that the 8 lanes are passed through the DSP MUL
                              by multiplying with 1. This mimics the pipeline delay vector MUL/MAC signal processing.
  3. my_stream_dm.cpp       : Based on direct stream access of the 32-bit AXI Stream. For AIE the native stream interface
                              is 32-bit, so for this example a temporary cint16 variable is used to pass input to output.
                              If used with vector register, the 4:1 conversion from 32 to 128-bit is better to use as this
                              aligns with the vector register. For that case 128-bit data is read every
                              4th clock cycle, corresponding to 4 cint16 samples. Similar argument for the output, 
                              128-bit data is written every 4th clock cycle and the 1:4 conversion to 32-bit stream.
```

For more details see [Datamover optimizations](./README_AIE_OPTIMIZATIONS.md#Datamover%20optimizations)



### AI Engine FIR filter example
To demonstrate how to use MATLAB and Python with Vitis Functional Simulation in a realistic DSP use case, the tutorial will use a 16 tap FIR filter.

#### Principle of operation for the FIR filter

The FIR filter operates by using the vector register as a tapped delay line with a convolution performed by a [sliding matrix multiplication operation](https://docs.amd.com/r/en-US/ug1079-ai-engine-kernel-coding/Multiple-Lanes-Multiplication-sliding_mul).


Parameters for the sliding multiplication operations:
 - With cint16 data and int16 coefficients, the AIE core can compute 16 MUL/MAC operations per clock cycle.
 - Considering only operations per cycle, this means the AIE core can compute one sample of a 16 tap FIR filter per clock cycle.
 - To translate this into vector operation, using 8 lanes, the AIE core compute 8 samples over 8 clock cycles.


#### Filter specification

| Property     | Type      | Buffer size | Target sample rate  | Description
| -------------|-----------|-------------|---------------------|---------------------------------------------------------
| Input data   | cint16    | 256         | 250 Msps            | Modestly set to match the MM2S/S2MM HLS blocks feeding the data.
| Coefficients | int16     | 16          | -                   | Assymmetric filter. Configurable by PS using RTP.
| Output data  | cint16    | 256         | 250 Msps            | Single rate filter, same as input.

#### Designing the FIR filter kernel
With the specified data and coefficient types, the AI Engine fixed point vector processor is capable of computing 16 operations per clock cycle.
This means the max theoretical throughput is 1250 Msps for AIE clocked at 1250 MHz.
A well designed, fully pipelined AIE kernel inner loop will be able to get close to this performance. Each time a function call is invoked, some 10s of clock cycles is needed for acquiring locks and replaying margin data.
This cause the actual throughput to drop depending on the buffer size.

Simplified, the throughput degradation can be estimated as:

***throughput<sub>actual</sub> = f<sub>aie_clk</sub> * t<sub>operations</sub> / t<sub>function</sub>***

Where ***f<sub>aie_clk</sub>*** is the AIE clock frequency, ***t<sub>operations</sub>*** the time spent on performing algorithmic computes.  
The ***t<sub>function</sub>*** is the time of all activities done by function call iteration like:
  - Lock management.
  - Initalize LUTs and parameters.
  - React and recover on stalls.
  - Replay margin overlap.
  - Treat conditional statements.
  - Format and rearrange data structures.

#### Planning the inner loop
To reach the maximum performance, all computes on the input data buffer needs to be scheduled and pipelined without any interruptions or stalls.
In practice this means the following coding techniques need to be used:
| Optimization technique     | Description
| -------------|-----------
| Zero overhead loop counter   | Is used on innermost loop and it automatically checks the loop exit conditions
| chess_prepare_for_piplining | Tells compiler to schedule instructions and have intermediate results be *in flight* in the pipeline registers
| Preamble the loop | Prepare the loop for uninterrupted execution by setting configurations and preloading vectors so the vector processor can start on first clock cycle in the loop.
| Software loop unrolling  | Manually replicate code patterns to avoid conditional statements and irregular jumps. This helps to get better utilization of the inner loop.

The AIE Compiler will automatically use the *Zero overhead loop counter* on inner loops, so the task here is to ensure it is the only loop needed.
The pragma for pipelining is to simply add the keyword in the for loop declaration.


For ***Software loop unrolling*** see details in [FIR Filter loop unrolling](./README_AIE_OPTIMIZATIONS.md#FIR%20Filter%20loop%20unrolling)
